# Kubernetes RBAC: permission generated from the code that needs it

**TL;DR: RBAC (Role-Based Access Control) answers "can this identity do
this verb on this resource." A `ClusterRole` lists allowed
(apiGroup, resource, verb) triples, a `ClusterRoleBinding` grants that
role to a `ServiceAccount`. This repo's role isn't hand-written, it's
generated from `+kubebuilder:rbac` comment markers sitting directly on
the code that performs each API call.**

## The three pieces, and how they connect

```text
ServiceAccount (checkout-gate-operator, in namespace checkout-gate-system)
   the identity the manager Pod actually runs as
        |
        | bound by
        v
ClusterRoleBinding (checkout-gate-operator-manager)
   "this ServiceAccount gets this ClusterRole"
        |
        | grants
        v
ClusterRole (checkout-gate-operator-manager)
   the actual permission list: apiGroups + resources + verbs
```

`ClusterRole`/`ClusterRoleBinding` are the cluster-scoped versions;
`Role`/`RoleBinding` are the namespace-scoped equivalents. This repo
uses the cluster-scoped pair because the controller needs to watch
`CheckoutGate` and `Deployment` resources across every namespace they
might exist in, not just the manager's own namespace.

## Why the role is generated, not written by hand

`config/rbac/role.yaml` doesn't exist because someone sat down and
wrote a permission list. It's generated by `controller-gen` reading
`+kubebuilder:rbac` markers scattered across the actual code:

```go
// internal/controller/checkoutgate_controller.go
// +kubebuilder:rbac:groups=checkout.gerardrecinto.dev,resources=checkoutgates,verbs=get;list;watch;update;patch
// +kubebuilder:rbac:groups=checkout.gerardrecinto.dev,resources=checkoutgates/status,verbs=get;update;patch
// +kubebuilder:rbac:groups=apps,resources=deployments,verbs=get;list;watch

// cmd/manager/main.go
// +kubebuilder:rbac:groups=coordination.k8s.io,resources=leases,verbs=get;list;watch;create;update;patch;delete
// +kubebuilder:rbac:groups="",resources=events,verbs=create;patch
```

```bash
go run sigs.k8s.io/controller-tools/cmd/controller-gen@v0.16.5 \
  rbac:roleName=checkout-gate-operator-manager paths="./..." \
  output:rbac:artifacts:config=config/rbac
```

The reason this matters more than it sounds: a hand-written RBAC role
tends to accumulate permissions nobody remembers granting, because
it's easier to add "just in case" than to prove a specific line is
unused. A generated role can only contain what the actual code
declares needing, right next to the line that uses it. Add a new API
call, add the marker next to it, regenerate, the role grows exactly as
much as the code actually requires and no more.

## Reading this repo's actual permission list

- `checkoutgates`: `get;list;watch;update;patch`, no `create` or
  `delete`, because the controller never creates or deletes
  `CheckoutGate` objects itself, only users do that.
- `checkoutgates/status`: a separate line from the base resource,
  because Kubernetes treats the `/status` subresource as its own
  permission surface, this is what lets a controller update Status
  without also being granted permission to edit Spec, a real
  least-privilege boundary, not a formality.
- `deployments`: `get;list;watch` only, this controller reads
  Deployments to check replica counts, it never modifies one.
- `leases`: needed only because `--leader-elect` uses a
  `coordination.k8s.io/Lease` object to decide which replica is
  currently the leader.
- `events`: `create;patch`, standard for any controller that wants to
  surface human-readable status via `kubectl describe`, not used
  heavily in this repo yet but declared honestly rather than omitted
  and silently failing later.
